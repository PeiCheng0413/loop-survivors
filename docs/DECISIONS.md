# 設計決策記錄

本文件記錄 2026-08-20 專案啟動討論的結論與**理由**。
理由比結論重要——日後若要推翻某條，必須先確認它的理由已不成立。

原則：**定案不翻案**。真要改，另開一次完整討論，並在本文件追加修訂段落。

---

## 1. 教學定位：練習場

學生已學過「重複執行」的基本語法，來這裡體會迴圈的**價值**與**設計感**。

**理由**：迴圈的難點從來不是語法，是「什麼時候該用」。彈幕遊戲讓迴圈的次數、
角度、間隔全部變成看得見的形狀，這個回饋迴路是講義給不了的。

**推論**：可以大膽做遊戲性，用關卡難度逼出迴圈需求，不需要手把手引導關。

## 2. 編寫時機：開局前 ＋ 升級時插積木

開局前寫好基礎攻擊腳本；每次升級暫停，三選一給卡，學生自己決定插在哪一層。

**理由**：讓 roguelike 的「build 成長」等同於「程式碼成長」。同一塊積木塞外層
或內層，彈幕形狀天差地別——**巢狀迴圈的概念用畫面就講完了**。

```
重複 8 次:            重複 8 次:
  旋轉 45 度            旋轉 45 度
  發射子彈              重複 3 次:      ← 新積木塞這裡
                          發射子彈
八方射線                八方三連發
```

## 3. 執行語意：每塊積木耗 4ms（本專案最重要的設計）

- 每塊積木執行消耗約 4ms（`BLOCK_COST`）
- `等待 (N) 秒` 是顯式的大額時間成本
- 整段腳本 = 一個攻擊週期，跑完後等冷卻再從頭執行

**理由**：這一條規則同時解決四件事。

1. **堵死「重複 9999 次」漏洞**，且是自我調節，不需要額外規則層
2. **保住八方齊射的視覺**：8 次迴圈（16 塊執行）= 64ms，體感幾乎同時
3. 給學生「程式執行有成本」的直覺——時間複雜度概念的雛型
4. **解鎖積木高亮**：因為執行有時間跨度，才能看見高亮在迴圈裡繞圈

第 4 點是最大的教學紅利。迴圈概念最難教的部分，是它在腦中是動態的、在紙上
卻是靜態的。這個機制讓那個動態直接演給學生看。

**成本曲線**（規則線性、體感非線性，學生不需被告知規則就會自己收斂）：

| 重複次數 | 一輪耗時 | 體感 |
|---|---|---|
| 8 | 64ms | 幾乎同時噴出，一朵花 ✅ |
| 30 | 240ms | 明顯掃射感，很帥 ✅ |
| 200 | 1.6s | 開始變鈍，玩家自己會嫌 ⚠️ |
| 9999 | 80s | 一輪都跑不完 ❌ 漏洞自動堵住 |

### 3a. 積木高亮用「餘輝」而非瞬間高亮（2026-08-20 實測後追加）

一塊積木只佔 4ms，畫面每 16.7ms 才畫一次 —— 實測每幀跑掉 **6 塊**積木，
但只畫得出最後採樣到的 1 塊，**六分之五的執行是隱形的**，看起來就是隨機亂閃。
整段腳本 5 幀跑完，接著 21 幀空白。

解法是餘輝：VM 記錄完整執行軌跡，HUD 每幀取走並把熱度衝到滿，
再以 **0.2 秒**衰減。一整幀跑過的積木同時發亮並逐漸退色，
迴圈變成一道看得見的行進波。

0.2 這個值是實際比對 0／0.12／0.2／0.3／0.45 之後選定的：散彈手一輪 418ms
＝執行 83ms＋冷卻 350ms，0.2 秒剛好涵蓋整段執行，又能在下一輪開始前退乾淨
留出黑暗間隙 —— 脈衝的節奏於是就是攻擊週期本身。太長（0.45）畫面永遠不會
全暗，變成一直亮著的糊團。

**這是純顯示層的修正，遊戲速度一格未改** —— 可讀性與遊戲性不必互相犧牲。
另加「本輪執行次數 ×24」：迴圈跑了幾次，用數字說比用動畫說更牢固，
動畫看過就忘，數字會留在畫面上被指著討論。

M1 接上 Blockly 後積木面積大很多，這個值可能要重新校一次。

**2026-08-21 更新**：積木面板改為只在暫停時出現後，Blockly 那側的餘輝
變成走不到的路徑（暫停時 VM 沒有執行）。逐步執行的顯示移到戰場左上角的
監視器，Blockly 只保留「本輪執行次數」，且改為面板拉出時才畫一次。

**警告**：4ms 是猜的，必須實測調整。但方向（小數字無感、大數字急速懲罰）是對的。
若設太大（如 50ms），八方齊射會變成慢吞吞的螺旋，經典彈幕造型全部做不出來。

## 4. 三層限制（各管一件事，不重疊）

| 限制 | 管什麼 | 教學作用 |
|---|---|---|
| 容量上限 | 腳本總長度（每塊積木 1 格） | 迴圈比展開寫划算 → 逼出迴圈 |
| 迴圈次數上限 | 單塊迴圈能跑多遠（初始 1～8） | 「迴圈上限 +2」成為可成長資源 |
| 稀有積木限量 | 強力積木的稀缺性（拿幾個放幾個，不可複製） | build 差異化 |

**容量上限的理由**：Blockly 支援複製貼上，學生可以把「旋轉 45 度 + 發射子彈」
貼八次，效果與迴圈**完全相同**。不處理的話，這遊戲只會教「重複勞動」。
容量上限把迴圈的本質（用更少的程式碼做更多的事）直接變成遊戲資源——學生不是
被規定要用迴圈，是**被逼到不得不發現迴圈划算**。

容量計算：C 形積木本身算 1 格，其內部每塊各算 1 格。

**已評估但不採用**：能量預算制（每發子彈耗能）雖優雅，但會是第四層規則，
學生要同時理解四種限制，認知負擔過重。三層是上限。

## 5. 積木語言（v1 共 8 塊，全繁體中文）

```
【控制】重複執行 (N) 次 { }        ← C 形，可巢狀，主角
        等待 (N) 秒
【發射】發射子彈
        方向旋轉 (N) 度            ← 相對
        方向設為 [最近的敵人 ▾]    ← 絕對
【狀態】子彈速度設為 (N)
        子彈大小設為 (N)
        子彈穿透設為 (N)
```

**狀態積木的教學價值**：它們讓「積木的順序」與「放在迴圈內或外」產生看得見
的差異，是繼巢狀迴圈之後的第二個教學點，實作成本卻幾乎是零。

**不放**條件判斷與迴圈變數 `i`：會稀釋迴圈這個主題。理由是主題稀釋，**不是
時間不夠**——所以時程變寬鬆也不該加回來。留給 v2 的進階挑戰模式。

**紅線**：絕不加入「散射 N 發夾角 M 度」這類一塊積木取代迴圈的設計。
那會讓學生不需要迴圈就能達成目的，直接摧毀整個教學前提。

全中文的理由：認知負荷該留給迴圈概念，不該分給英文單字。

### 5a. 基本積木一開始就全有，升級卡只發稀有積木（2026-08-20 補洞）

原本 §5 定了八塊基本積木、§7 定了升級發積木卡，但沒寫清楚**哪些積木一開始
就有、哪些要靠抽**。此處補上。

- **基本八塊**：開局就全部在工具箱裡，無限供應，只受**容量**限制
- **稀有積木**：只能從升級卡取得，拿幾個放幾個（`maxInstances`），不可複製

**理由：核心教學點不能被骰子決定。** 若「重複執行」要靠升級抽到，就會出現
「這個學生整局沒抽到迴圈積木」的情況 —— 那不是運氣差，是這堂課對他失效了。
教學工具不能有這種失敗模式。

§2 的「拿到積木、決定插在哪一層」那個時刻完整保留，只是主角從基本積木換成
稀有積木。所以這是補洞，不是翻案。

**待設計（M2 做升級卡時定）**：稀有積木的具體清單。候選是效果類而非控制流類
（爆裂彈、追蹤彈、分裂彈、反彈彈）—— 控制流積木若做成稀有，等於把教學核心
交給運氣，違反上面的理由。

**連帶問題（未解）**：`等待` 目前是唯一「放了就純虧」的積木 —— 散彈手加一塊
迴圈內的 `等待 0.1 秒`，週期從 418ms 變成 1218ms，DPS 掉到三分之一，沒有任何
補償。它既然不會被抽到廢牌了，問題從「抽到很嘔」變成「永遠沒人用」，
八塊積木實際只有七塊。候選解法是**蓄力**（子彈傷害隨距上一發的間隔成長），
好處是位置會產生巨大差異（迴圈內每發滿蓄力 vs 迴圈外只有第一發），
與巢狀迴圈教的是同一件事。待 M1 拖過積木後再定。

### 5b. Debuff 積木的補償設計（2026-08-20 定案）

**問題**：八塊積木裡有四塊沒有決策 —— `等待` 是純虧（放了就變弱），
`速度`／`大小`／`穿透` 則是「設到最大就對了」。沒有取捨就沒有策略，
學生拖完一次就再也不會思考這些積木。

**解法：debuff 分類，各配一種補償機制。**

| Debuff 類型 | 補償機制 | 領域 |
|---|---|---|
| 延遲類（等待） | **蓄力** —— 距上一發越久，這發越強 | 時間軸 |
| 子彈參數類 | **火力換機動** —— 規格越高，角色移速越慢 | 攻防平衡 |
| 清版需求 | **能量 ＋ EX 積木**（待做） | 資源管理 |

**蓄力**（`CHARGE`）：傷害倍率 0.45 ～ 2.6，蓄滿需 0.3 秒。教學價值在於
**位置會產生巨大差異** —— 等待放在迴圈內，每發都滿蓄力；放在迴圈外，
只有第一發受惠。這跟巢狀迴圈教的是同一件事，換了個維度。

**火力換機動**（`MOBILITY`）：負載取腳本中**出現過的最高規格**，而非實際
發射時的值 —— 這樣學生無法用「設高再設回來」鑽漏洞，規則也維持可預測
（拖積木的當下就看得到移速變化）。反向同樣成立：自願降規格換更快的走位，
是完全正當的另一種 build，不是懲罰。

**EX 技能必須做成積木，不能做成按鍵。** 按鍵版會違反 §6 —— 一個能清版的
按鍵會讓按得準的學生贏過寫得好的學生。做成積木後，決策變成「要不要放進
腳本、放在迴圈內還是外、冷卻沒好時怎麼辦」，清版能力於是是程式設計問題
而非反應問題。天生適合當稀有積木（`maxInstances: 1`）。

**迴圈紅線驗證**（`npm run sim -- 300`，2026-08-21 無盡循環版）：

```
腳本        每秒傷害  擊殺   等級  存活
巢狀測試      329.6   2676   13   293s    巢狀迴圈
螺旋手        141.7    805    6   220s    迴圈變數
連射狙擊       77.0   1699    6   205s    瞄準 ＋ 迴圈
散彈手        124.5    442    6   121s    散射迴圈
狙擊手         60.1    563    7   120s    瞄準，**無迴圈**
機槍手         66.3    365    5   112s
```

**最重要的是狙擊手與連射狙擊這組受控對照**：同樣的瞄準、同樣的子彈規格、
同樣的容量，唯一差別是發射有沒有包進迴圈 —— 存活 120s → 205s，多撐 71%。

先前的比較（散射 vs 瞄準）混入了命中率這個變數，證據力較弱。
這組把變數隔離掉了：**同一個 build 加上迴圈就是會變強**，
而巢狀迴圈又明顯強過單層。紅線守住。

**兩個誠實的但書**：

1. **擊殺數與 DPS 不同調**：狙擊手 DPS 最低卻擊殺最多，因為它每發都瞄準，
   而散射流大部分子彈落空。這不是蓄力的問題，是命中率維度 —— 而且它導向
   一個好的學習：**迴圈＋瞄準的組合才是最強解**，值得讓學生自己撞出來。
2. ~~**蓄力的真正回報要等高血量敵人**~~ → **已解決（2026-08-21）**：
   敵人血量隨時間成長（`ENEMY.hpGrowthPerMinute`），且裝甲兵有傷害門檻 ——
   單發低於門檻完全無效，蓄力從「略有優勢」變成「唯一解」。

### 5c. 積木擴充（2026-08-20，M2 後）

原本 §5 只定八塊，且刻意排除迴圈變數。這次擴充**沒有推翻那個理由**：
當時排除的是「完整的變數系統」，因為它會把主題從迴圈拉到變數。
以下新增的積木都是往**迴圈更深處**走，而不是往旁邊擴散。

| 新積木 | 教的是什麼 |
|---|---|
| `方向旋轉 (N) 度 × 迴圈次數` | **迴圈變數的輕量版** —— 第一次能用到「現在是第幾圈」，畫出來就是螺旋 |
| `子彈速度增加 (N)` | **累加器** —— 放進迴圈就會一次比一次快，重複做加法會一路長上去 |
| `子彈大小增加 (N)` | 同上，換一個維度 |
| `子彈存活 (N) 秒` | 參數搭配 —— 速度 × 存活 = 射程 |
| `子彈改為分裂`（稀有） | build 變化 |

**迴圈變數為什麼用「× 迴圈次數」而不是真正的變數**：真變數需要運算式系統
（值也要是積木），那是另一個量級的複雜度，而且會讓學生開始處理「變數該叫
什麼名字」這種與迴圈無關的問題。單一積木把圈數變成可用的量，教學收益幾乎
相同，成本卻低一個數量級。

**累加器積木的價值**：`子彈速度增加 60` 放在迴圈外只加一次，放在迴圈內
會加 N 次 —— 又一個「位置決定結果」的例子，而且它教的是程式設計裡
最基本的累加模式。

**紅線仍然守住**：新積木沒有任何一塊能取代迴圈。`× 迴圈次數` 反而只有在
迴圈裡才有意義，等於是在獎勵使用迴圈。

### 5c-2. 第二批擴充（2026-08-22，實測反映積木太少）

| 新積木 | 教／玩的是什麼 |
|---|---|
| `子彈轉向 每秒 (N) 度` | 與迴圈**相乘**：八方射線每發都彎就成了旋渦 |
| `發射點距離設為 (N)` | 位置也是參數。配合旋轉迴圈就是一圈發射點 |
| `等待 (N) 秒 × 迴圈次數` | 漸慢的節奏，與「方向旋轉 × 迴圈次數」同一家族 |

選這三塊的準則是**與迴圈相乘、而不是取代思考**：它們讓同一個迴圈畫出完全
不同的圖形，而不是讓學生少寫一個迴圈。

**再次確認排除條件判斷（`如果...那麼`）**：§5 當初的理由是「稀釋迴圈主題」，
但在 §9a 定案之後有更嚴重的問題 —— **它會把核心賣點自動化掉**。學生若能寫
「如果 敵人很多 那麼 散射」，就不必在階段切換時暫停、思考、重排積木，
程式會自己處理。那會讓這款遊戲變成「寫好放著跑」，與「依敵人重新排列積木」
的整個設計直接衝突。這條排除從此是**結構性的**，不會因為想增加積木種類而鬆動。

## 6. 玩家操作：只能走位，不能瞄準

WASD／方向鍵移動，滑鼠完全不參與戰鬥。

**理由**：若允許滑鼠瞄準，遊戲會退化成**手速競賽**——手殘的學生就算寫出漂亮
的巢狀迴圈也打不贏，反應快的學生隨便寫兩塊積木也能過關。那等於告訴學生
「程式寫得好不重要」，教學前提直接崩掉。

砍掉瞄準後因果關係變得乾淨：**打得贏 = 腳本設計得好**。輸了，學生唯一能檢討
的就是自己的程式碼——這正是我們要的歸因方向。

「瞄準」交給 `方向設為 [最近的敵人 ▾]` 積木處理，把手速轉譯成邏輯決策。

## 7. Roguelike：混合獎勵，保底一張積木卡

- **積木卡** → 進工具箱，學生自己決定插哪一層
- **數值卡** → 進側邊屬性面板，**不進腳本**
- **進化卡** → 屬性面板（特殊效果）

**理由**：純積木卡會導致腳本膨脹（20 級後腳本 20 塊，週期長到荒謬），且失去
數字變大的爽感。混合設計讓積木卡負責 build 變化、數值卡負責成長曲線與平衡旋鈕。

**數值卡不進腳本**是硬性規定：腳本區只放有控制流的真積木，學生看腳本時，
看到的每一塊都跟程式邏輯有關，認知不被稀釋。

這也收編了「開局設定角色參數」的原始構想——參數確實存在，但它們是升級累積
出來的屬性面板，不是沒有控制流的假積木。

暫停時**整份腳本可自由重組**，不只是插入新積木。理由：只能插入的話，學生第一
次放錯就毀掉整局，挫折感會壓過學習動機。

## 8. 試射預覽視窗

暫停編輯時，腳本區旁一塊小畫布即時循環播放當前腳本的彈幕形狀 ＋ 積木高亮。

**理由**：若只能靠實戰驗證，回饋週期是**一整局**——那不是設計，是賭博。
而且失敗成本高到學生會傾向「不要亂改，能動就好」，正好扼殺我們要的實驗行為。
預覽把「假設 → 驗證」的迴路從一局壓縮到兩秒。

**不做完整除錯器**（單步、中斷點、變數檢視）：那是給程式設計師的工具。
學生要的不是檢查變數值，是看到形狀——彈幕本身就是最好的視覺化輸出。

**架構要求**：VM 與 renderer 從 M0 起就必須寫成可獨立呼叫的模組。事後補會很痛。

## 9. 局長與流程 —— **無盡模式**（2026-08-21 改版）

~~遊戲內 5 分鐘，時間到出王~~ → **改為無盡**：遊戲不會結束，敵人持續變強，
每隔一段時間出現一次王。玩家死亡才結束，成績就是**存活時間**。

參照 Google 小恐龍：隨時能開始、死了立刻重來、分數只有一個數字。

### 階段循環（每一輪比上一輪強）

```
蟲群 → 裝甲兵 → 疾行群 → 護盾兵 → 王 → （下一輪，強度提升）
```

王不再是結局，而是**節拍器** —— 每個循環一次，用來標記「你又撐過一輪」。
敵人的血量與數量隨時間無上限成長（原本 `SPAWN.cap` 的上限要拿掉）。

### 為什麼改：重玩動機

固定五分鐘的局，打完就沒事了；無盡模式的成績是一條可以一直推的線，
而推線的方法**只有把程式寫得更好**（走位的上限很快就到頂）。
這讓「回去改腳本」變成玩家自己想做的事，而不是被規則要求。

### 這一改帶來的課堂風險（**未解**）

原本「5 分鐘一局、一節課跑 3 局」的節奏是為了保證**每個學生都看得到
所有教學內容**。無盡模式下，教學內容被**存活能力**擋住了：

- 撐得久的學生會遇到護盾兵、王、箭矢解鎖
- 一直死在第一分鐘的學生，永遠碰不到「切換排列」這個核心賣點

這是無盡模式的真實代價，必須設計對策。目前的候選：

1. **第一輪循環刻意做得很緩**，確保任何人都能撐到第一隻王（目標 2 分半內）
2. **循環週期要短**（王每 2～3 分鐘一次），而不是十分鐘才見一次
3. 老師可調的難度倍率（沿用 §9 原本「局長可調」的精神）

**第 1 點是硬需求**：如果班上有學生整節課沒看過護盾兵，那這堂課對他而言
就沒有發生過。難度曲線的前段是教學設施，不是遊戲平衡。

### 積木面板只在暫停時出現（2026-08-21）

玩的時候戰場佔滿畫面，暫停才把積木面板拉出來。

這與暫停既有的用途一致 —— 升級選卡、依敵人改排列、檢查護盾幾何，
全都發生在暫停時。積木在遊戲進行中根本沒有使用時機，讓它常駐只是
壓縮戰場並讓畫面看起來很忙。

**開局停在準備狀態**：面板是拉開的，學生先看到自己的攻擊腳本與預覽，
按空白鍵才開始。若一開局就直接開打，多數人不會發現左邊可以編輯。

**不變條件：面板開著 ⇔ 遊戲暫停。** 玩到一半手動把面板拉出來也會自動暫停，
否則會出現一邊被追殺一邊拖積木的荒謬狀況。

### 死亡與重來

死亡後可用同一份腳本立刻重來 —— roguelike 的學習發生在重跑，
每次從零拖積木的摩擦力會殺掉重玩意願。

**結算畫面（2026-08-22）**：顯示存活時間、撐過幾輪、擊殺、等級，
以及本機前五名（存 localStorage，§11 的零後端方案）。

最重要的是那一句**針對這一局的建議**。死亡是學生最願意接受建議的時刻，
而「你撐了 2 分 10 秒」本身不會讓人知道下一步該改什麼。建議依
**腳本結構與死亡當下的階段**產生，優先序由根本到細節：

1. 整份腳本沒有迴圈 → 先教迴圈，其餘都不重要
2. 死在某階段而缺對應的積木 → 指出那個階段要的排列
3. 容量沒用完 → 提醒還有空間
4. 沒用巢狀 → 推一把
5. 都沒問題 → 提示下一局試著在階段切換時換排列

這是遊戲裡唯一會**主動教學**的地方，其餘都靠學生自己撞出來。
放在死亡時是因為那時他正好想知道「我哪裡做錯了」。

## 9a. 適應性重編程 —— 本作的核心賣點（2026-08-20 定案）

**同一段迴圈，換個排列方式，就從掃蕩變成穿刺。** 玩家依照當前敵人的種類
暫停、重新排列積木 —— 程式結構因此不只是 build，而是**戰術**。

這是本專案唯一「非它不可」的東西：講義教不了「結構要服務意圖」，
但玩家會在被裝甲兵擋下來的那一刻自己學會。

### 硬前提：不能有全能解

若某種排列在所有情況下都最強，玩家找到最優解後就再也不會改，賣點變裝飾。
2026-08-20 的實測顯示**目前正是如此**（巢狀迴圈與狙擊流全程通吃）：

```
巢狀測試  擊殺 3835  撐完      散彈手    擊殺 1661  247s
狙擊手    擊殺 1950  撐完      連射狙擊  擊殺 1073  170s
```

所以敵人必須具備**結構弱點**，而不只是血量高低的差別。

### 敵人的結構弱點

| 敵人 | 特性 | 逼出的排列 |
|---|---|---|
| 蟲群 | 數量極多、血極少、四面包圍 | 散射迴圈（旋轉＋發射繞一圈） |
| 裝甲兵 | **傷害低於門檻完全無效** | 蓄力：等待進迴圈，少而重的子彈 |
| 護盾兵 | **短時間內命中 3 次才破盾**，否則無敵 | `方向設為最近的敵人` ＋ `重複 3 次 { 發射 }` |
| 疾行群 | 數量極多、移動極快、傷害低 | 最多方向 × 最多子彈，覆蓋面優先 |
| 王 | 單一目標、血極厚 | 定向連射（面向敵人＋純發射迴圈，不要旋轉） |

**護盾兵與裝甲兵刻意要求相反的排列**：一個要三連速射、一個要單發重擊，
兩者無法同時滿足。這不是設計缺陷，正是切換機制的價值所在 —— 但因此
**它們必須分在不同階段**，同時出現會讓玩家陷入無解，那是挫折而非挑戰。

護盾兵與裝甲兵的差別也值得說明：裝甲兵考的是**單發威力**（空間維度），
護盾兵考的是**時間內的節奏**（時間維度）。同一個「打不動」的表象，
背後是兩種完全不同的程式結構。

**裝甲兵的傷害門檻是關鍵設計**：單純的數值差異玩家會硬吃，只有**質變**
（完全打不動）才逼得動人去改程式。

### 節奏：一局四次切換，不是結尾一次

§9 原本定「五分鐘到出王」，那樣整局只換一次排列，不足以成為節奏。改為階段輪替：

```
蟲群 → 裝甲兵 → 疾行群 → 護盾兵 → 王 → （循環，強度提升）
```

無盡模式下（§9 改版）階段是**循環**而非一次性時間軸，王是節拍器不是結局。
實際數值見 `config.ts` 的 `PHASES`，該處為唯一真實來源。

階段切換前預告並**自動暫停**。不自動暫停的話，多數學生會硬打到死，
根本不會發現可以改程式 —— 而那正是整個機制的價值所在。

### 摩擦力：先手拖，後期解鎖槽位（2026-08-22 已實作）

換排列若每次都要重拖，玩家會嫌麻煩而不改，機制就死了。解法分兩段：

- **前期只能手拖**，且敵人設計成「拖一兩塊就能轉換」（例如把旋轉積木拖出迴圈）
- **後期打贏王解鎖「腳本槽位」**，最多 3 套，數字鍵即時切換

順序不能反：一開始就給槽位的話，學生會變成切換預存檔，永遠不會真的理解
排列的意義。手拖階段是學習，槽位是給已經學會的人的獎勵。

實作要點：

- **解鎖跨局保留**（localStorage）—— 它是「永久能力」，不該因為重開一局收回
- **新槽位複製當前腳本當起點**，不留空白：空的槽位在戰鬥中毫無用處，
  學生也不可能在被追殺時從零拖一套。從現有的複製一份再改才是真實用法
- **切換不需要暫停**：那正是這個獎勵的價值 —— 把「換排列」從幾十秒縮到一個按鍵
- **數字鍵開打前選角色、開打後切槽位**：兩者不會同時有意義，
  共用同一排按鍵，學生不必再記一組
- 解鎖第二格之前完全不顯示槽位介面：在那之前它只是一顆沒用的按鈕，
  反而讓學生以為自己漏了什麼功能

## 9b. 幾何護盾：畫出形狀來防禦（2026-08-21 改版，取代飛行箭矢）

學生用積木畫出一個封閉多邊形，那個形狀**就是護盾的邊界**。

- 敵人碰到護盾會被彈開
- 護盾有血量，破掉後需要時間恢復
- 護盾存在期間提供 buff，**強度依圖形的難易度**
- 形狀是靜態的：只在腳本改動時算一次頂點，**不需要每幀運算**

### 為什麼比原本的「飛行箭矢」好

原本的設計是箭矢沿著路徑飛，圖形只是它走過的軌跡 —— 短暫、要每幀跑 VM、
而且形狀畫完就消失。護盾把同一個幾何練習變成**持續存在的東西**：

| | 飛行箭矢（已放棄） | 幾何護盾 |
|---|---|---|
| 運算 | 每幀執行腳本走路徑 | 腳本改動時算一次頂點 |
| 形狀的意義 | 軌跡，會淡掉 | **防禦邊界**，一直在 |
| 畫錯的後果 | 圖形不好看 | **護盾有缺口，敵人穿得進來** |

最後一列是關鍵：畫錯不再只是「不好看」，而是**看得見的破綻**。
自我檢查的性質從「有沒有閉合」升級成「你的防線哪裡有洞」。

### 已驗證的幾何基礎（2026-08-21 原型實測）

前進／右轉積木與正 n 邊形的判定在箭矢原型中已經驗證過，該部分直接沿用：

```
✅ 正六邊形    終點距起點 0.0px    最終朝向 0°
❌ 六次轉45度  終點距起點 110.6px  最終朝向 270°
```

轉角算錯時**最終朝向**也會偏掉，正好可以生成「轉角總和只有 270 度，
還差 90 度」這種可教的回饋 —— 不是只說「沒有生效」。

### 沒閉合＝完全沒有護盾（2026-08-21 定案）

不是「有缺口的護盾」，是**完全沒有**。二分法比部分生效好教：
「你沒有護盾，因為圖形差 90 度沒接上」遠比「你的護盾有點漏」清楚。

戰場上也**不顯示**未閉合的形狀 —— 半個護盾在畫面上只會製造誤解。

那學生怎麼看自己畫錯在哪？**在暫停時的預覽視窗裡看**：預覽會跟著分頁
切換內容，看護盾分頁時顯示形狀本身，並把起點與終點各標一個點、
中間拉一條紅色虛線。學生看到那條線就知道少轉了一個角，不必讀任何數字。

這也讓「暫停」多了一個用途：它不只是升級與改排列的時機，也是**檢查幾何**
的時機 —— 判斷在預覽時就做完，回到戰場時結果已經確定。

### 待定問題

1. **buff 的種類**：邊數決定強度已定，但強化的是什麼？（傷害／移速／回復？）
   目前實作為傷害。
2. **護盾大小的取捨**：大盾覆蓋廣，是否該用較低的血量或較慢的回復來平衡？

## 9c. 解鎖階梯與雙腳本驗證（2026-08-21）

### 每打贏一次王解鎖一項永久能力

```
第 1 隻王 → 攻擊模式記憶槽（模板切換）
第 2 隻王 → 新武器（不同武器需要不同的積木排列）
第 3 隻王 → 魔法箭矢
```

搭配 §9 的無盡模式，王是節拍器也是**解鎖節拍** —— 每撐過一輪就多一個
能力，成長感與課程進度同步推進。

### 兩件事必須分清楚，風險差很多

| | 是什麼 | 複雜度 |
|---|---|---|
| 記憶槽／模板切換 | 同一份攻擊腳本的多個存檔，一次只有一個生效 | 低 |
| **雙腳本並行** | 攻擊腳本 ＋ 箭矢路徑，**同時運作** | **高，未驗證** |

解鎖順序把記憶槽排在前面、箭矢排在後面，但**風險順序剛好相反**。

### 先做技術驗證再往下蓋（2026-08-21 決定）

「不同武器需要不同積木排列」這整套構想，成立的前提是**學生管得動一份
以上的腳本**。若管不動，箭矢、多武器、模板切換全部要重新設計 ——
所以在蓋任何一層之前，先用拋棄式原型回答這幾個問題：

1. **技術**：同一頁兩個 Blockly 工作區會不會互相干擾（工具箱、undo、焦點、
   拖曳範圍）？
2. **版面**：400px 的面板放得下切換介面嗎？兩份腳本要能同時看見嗎？
3. **認知**：學生會不會忘記另一份腳本的存在？
4. **切換成本**：要改箭矢路徑時，會不會因為要切分頁而懶得改？

**放棄條件**：若第 1 點出現無法繞過的技術問題，或第 3 點在實測中明顯成立，
就把箭矢改成「不需要第二段腳本」的設計（例如路徑從幾個預設圖形中選）。

## 9d. 武器系統（2026-08-21 提案）

武器可切換，**每打贏一隻王解鎖一把**。不同武器需要不同的積木排列，
再與 §9a 的敵人結構弱點交叉，形成「敵人 × 武器 × 排列」的三層搭配。

### 已構想的武器

| 武器 | 特殊積木 | 教的概念 |
|---|---|---|
| 基本射擊 | （現有八塊） | 迴圈、巢狀、累加器 |
| **接觸觸發** | `當碰到敵人時 { ... }` | **事件驅動**：程式不只是從上跑到下，也可以「被觸發」 |

`當碰到敵人時` 是本專案第一個**事件積木**，教的東西與迴圈互補：
迴圈是主動重複，事件是被動回應。內層可以放任何攻擊排列，
因此它同時是「把既有知識用在新脈絡」的練習。

### 已放棄

**魔法箭矢**：原本要做成專門攻擊的武器，但搭配的積木尚未想清楚。
與其硬做，不如先空著 —— 護盾已經承接了它的幾何教學價值。

## 10. 開局起點：3 張角色卡，各附起手腳本

```
【散彈手】容量 12          【機槍手】容量 10         【狙擊手】容量 8
重複 8 次:                 重複 3 次:                方向設為 最近的敵人
  方向旋轉 45 度             發射子彈                 子彈速度設為 600
  發射子彈                   等待 0.1 秒              發射子彈

單層迴圈 + 角度            單層迴圈 + 節奏           無迴圈，高單發威力
```

**理由**：空白畫布是新手最大的挫折來源。且對我們特別不利——第一局若要從零思考
攻擊該長什麼樣，學生多半拖出「發射子彈」就開打，根本碰不到迴圈。

起手腳本是**免費的範例教學**：學生一開局就看到一段能動且明顯有效的迴圈，然後
會做我們最想要的事——改改看數字。8 改成 16 會怎樣？45 度改成 30 度會怎樣？

**狙擊手刻意不含迴圈**：選它的學生會很快發現火力不足，主動去想「我是不是該加個
重複」。那個時刻就是我們要的。

**擴充點**：老師可自行新增角色與起手腳本，用角色卡設計課堂主題。想上巢狀迴圈
那節課，就放一個起手腳本已含巢狀結構的角色。

## 11. 技術選型

| 項目 | 決定 | 理由 |
|---|---|---|
| 前端骨架 | **vanilla TS + Vite**，不用 React | Blockly 與遊戲迴圈都是命令式的，React 在中間只會變成要繞過的障礙。60fps 的遊戲資料本來就不能進 React state，最後 React 只剩下畫幾個選單——那不如不要 |
| 積木編輯器 | **Blockly 13 + zelos renderer** | zelos 是官方內建的 Scratch 風格外觀，學生看起來就是 Scratch，底下卻是維護良好的現代函式庫。免費送拖放、巢狀、序列化、動態工具箱、Undo |
| 渲染 | **原生 Canvas 2D**，無遊戲引擎 | 難點是自製 VM 與彈幕碰撞，引擎一個都幫不上；物理引擎對彈幕遊戲反而是負擔。已背 Blockly 約 800KB，不宜再疊 Phaser 1MB+ |
| 後端 | **無**。localStorage + 本機排行榜 + Base64 分享碼 | v1 要驗證的是「好玩嗎、學生真的會撞出迴圈嗎」。這兩件事沒驗證前做後端，是把力氣壓在最不確定的假設上 |
| 美術 | 全 Canvas 幾何繪製，**零圖檔** | 彈幕遊戲與幾何風天生相配，無版權問題，部署乾淨 |
| 音效 | WebAudio 即時合成，**零音檔** | 零版權、零下載體積 |

**已評估但不採用**：
- scratch-blocks——無 ESM build、Vite 整合痛苦、文件稀少；外觀優勢已被 zelos 抵銷
- 自製積木 UI——巢狀拖放判定（要能插進 C 形積木內部第 3 行）是爛坑，做出來還比 Blockly 難用
- PixiJS——效能天花板用不到；渲染集中在單一模組，真要換也不必動遊戲邏輯

**效能保險**：全域子彈數硬上限（`MAX_BULLETS`），超過不生成。不對學生說明，
純粹防止極端情況把瀏覽器打爆。

## 12. 敵人（v1 三種）

直衝型、繞行型、遠程型——彈幕遊戲的最小威脅集合，能逼出不同的走位與腳本策略。

## 未解風險

1. **平衡是長尾**。M0～M3 約兩三週到「能玩」，但「好玩」要靠反覆試玩調整，無法給時程保證。
2. ~~**Blockly 三處 API 未驗證**~~ → **已驗證通過（2026-08-20，Blockly 13.2.1）**

   | 需求 | API |
   |---|---|
   | 只能用特定積木 | 工具箱定義；`workspace.updateToolbox()` 動態解鎖 |
   | 容量上限 | `maxBlocks` ＋ `remainingCapacity()` |
   | 稀有積木限量 | `maxInstances: { type: n }` ＋ `remainingCapacityOfType()` |
   | 稀有積木不可複製 | **自動**：達到 maxInstances 時 `isDuplicatable()` 回傳 false |

   三層限制規則全部有原生支援，不需要自製積木 UI。且 Blockly 數積木的方式
   （每塊 1 個、C 形本身也算 1 個）與我們的容量規則完全一致，不必自寫計數器。

   **待定細節**：`remainingCapacity()` 實作為 `maxBlocks - getAllBlocks(false).length`，
   會把學生拖出來放旁邊、未接上腳本的散塊也算進容量。傾向接受此預設
   （逼學生保持工作區整潔，也更貼近「記憶體」的隱喻），M1 實際操作後再定。
3. **4ms 是猜的**，必須實測調整。
4. **容量計算的巢狀規則**已定（C 形本身 1 格、內部各 1 格），但學生取捨手感待驗證。
